Q.7r — NBSP: чтение текста ячейки без подмены NBSP (замена гибрида 14 сайтов)
 Идея: QTextDocument.toPlainText() подменяет U+00A0 на пробел, из-за чего NBSP теряется при ЛЮБОЙ правке ячейки (не только при программной вставке).
 QTextDocument.toRawText() этого не делает (возвращает сырой текст, абзацные/строчные разделители U+2029/U+2028 вместо '\n').
 Шаг 0 (до правок, пробой на offscreen Qt): подтвердить в PyQt6 6.11, что (а) setPlainText с NBSP сохраняет NBSP в документе, (б) document().toRawText()
   возвращает NBSP, (в) после замены U+2029/U+2028/U+FDD0/U+FDD1 так, как это делает toPlainText, результат равен toPlainText с единственной разницей — NBSP,
   (г) NBSP сохраняется после ручной правки соседнего символа (QTest.keyClick). Если хотя бы (а) или (б) не подтверждается — НЕ править код, остановиться и описать,
   вернуться к гибриду из отчёта Q-B §5.4 только по моему вердикту.
 Реализация (если шаг 0 зелёный): один хелпер (например, _cell_text_keep_nbsp(widget): toRawText + замены разделителей, тот же результат, что toPlainText, но без NBSP→пробел).
   Использовать:
   1. в on_target_text_changed (Supervertaler.py:33145–33155, не-WYSIWYG ветка);
   2. WYSIWYG-ветку (_wysiwyg_document_to_tagged_text) — сначала проверить, теряет ли она NBSP; если да — исправить минимально, если нет — оставить;
   3. в местах, где после вставки код читает ячейку через toPlainText() и записывает/сравнивает с моделью (список в Q-B §5.2, поле «читают toPlainText ПОСЛЕ вставки»).
   Остальные чтения toPlainText (для UI, поиска и т. п.) — НЕ менять; в отчёте перечислить, где ячейки читаются в модель.
 Не делать: blockSignals на 14 сайтах, починку мёртвой явной записи (:35891–35896, :7527–7533), удаление mark_segment_modified (идёт в 8.18).
 Проба: NBSP-источник → (а) Ctrl+N/Paste из панели QuickTrans, (б) вставка TM, (в) пакетный перевод, (г) ручная правка соседнего символа, (д) Ctrl+T —
   во ВСЕХ случаях segment.target содержит '\xa0' (и экспорт txt/docx/tmx его сохраняет). Для каждого пути — регрессия: статусы, undo, TM-запись, превью как до правки.
   Известные пары: обработчик-guard «new_text == old_target» теперь сравнивает сырой текст; убедиться, что идемпотентность не сломалась (повторная программная вставка того же текста не плодит undo).

Q.8b — подключение и таймаут (замена рекона; реализация с предварительной проверкой гипотезы)
 Наблюдение Дмитрия: недоступный хост в локальной сети (ПК выключен/сервер остановлен) даёт сообщение «timed out after 10 minutes (600 s)» через ~65 с
 (MT 1:07, AI/LLM 1:05). Гипотеза: это TCP-connect timeout Windows (~21 с) × 3 попытки SDK (max_retries=2) + паузы; httpx.ConnectTimeout openai превращает в APITimeoutError,
 а llm_clients пишет в сообщении read-таймаут профиля.
 Шаг 0 (проба, до правок): воспроизвести на fake-окружении (адрес из TEST-NET-1, например 192.0.2.1:port, с timeout_min=0.05 и с дефолтом), показать
   время до ошибки, класс исходного исключения (APITimeoutError vs APIConnectionError, __cause__ = httpx.ConnectTimeout/ConnectError) и текст итогового сообщения.
   Дополнительно: закрытый порт на 127.0.0.1 (мгновенный отказ) и сервер, принявший соединение и молчащий (настоящий таймаут чтения) — все три случая в таблице.
   Если гипотеза не подтверждается — остановиться, описать, код не править.
 Реализация (если подтверждена):
   1. Отдельный таймаут подключения 15 с (httpx.Timeout(connect=15, read=<timeout профиля>, write=…, pool=…) — как принято SDK) во ВСЕХ местах создания клиента llm_clients
      (клиент, vision-путь, MT-путь). Таймаут чтения остаётся от timeout_min профиля.
   2. Ошибки подключения (ConnectTimeout, ConnectError, APIConnectionError без ответа сервера) → новый тип LLMConnectionError (подкласс LLMResponseError, как у остальных)
      с сообщением одной строкой: «Cannot connect to <host:port> within 15 s — host unreachable or server stopped — profile 'Имя'.» Без упоминания таймаута чтения.
      Настоящий таймаут чтения (сервер принял соединение и молчит) остаётся LLMTimeoutError с прежним текстом.
   3. Повторные попытки SDK на ошибках ПОДКЛЮЧЕНИЯ: не повторять (max_retries=0 для connect-ошибок), иначе 3×15 с. Повторы на 5xx и прочем оставить как есть
      (проверить, как это сейчас устроено в llm_clients; если retries задаются на клиенте целиком — предложить вариант и описать, не ломая 5xx-повторы).
   4. QuickTrans: строки ошибок остаются в форме «[Error: …]»; старый текст «[MT proxy not running. Start it.]» для закрытого порта на localhost оставить как есть
      (не менять поведение, которое Дмитрий уже проверял), но connect-timeout к удалённому хосту должен давать новое понятное сообщение.
   Пробы: три случая из шага 0 с новыми ожиданиями (время до ошибки ≤ ~15–20 с для недоступного хоста; сообщение корректное; чтение — прежнее время и текст);
   регрессия тел запросов (байт-идентичны), пробы G3.2/Q-A (таймаут чтения, усечение, профили) проходят без изменений. Известное: Windows-поведение TEST-NET проверяется на локальной
   машине агента; если TEST-NET в среде ведёт себя иначе (мгновенный отказ), использовать блокирующую ловушку-сокет.
