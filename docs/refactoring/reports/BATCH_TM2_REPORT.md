## 1. Разведка (до правок; цифры из `tm2_recon_before.py`, прогон 2026-11-16)

### 0a. Как работает фильтр сейчас

Механизм (`refresh_browser`, `modules/tm_manager_qt.py`, до-код :777–847):

- при непустом поле Filter вызывается `db_manager.concordance_search(filter_text)`
  (`modules/database_manager.py:2265`);
- внутри — **FTS5**-запрос `MATCH '"<query>"'` по виртуальной таблице
  `translation_units_fts` (токенизатор по умолчанию **unicode61**), `ORDER BY
  modified_date DESC LIMIT 100`; при исключении FTS — **fallback на SQL LIKE**
  `%<query>%` (тоже LIMIT 100);
- фильтрация идёт **в БД по ПОЛНОМУ тексту** обеих колонок (Source + Target —
  режима «Search in» не существовало); TM-фильтр диалога накладывается **Python-ом
  ПОСЛЕ** LIMIT 100; лимит «Show: N» на путь фильтра **не влияет вообще**;
- `concordance_search` не экранирует `%` и `_`: на FTS-пути они сепараторы
  токенов, на LIKE-пути — **wildcards**.

Экспериментальные цифры (тестовая БД, N=6, из recon-теста):

| Запрос | FTS-путь (здоровый индекс) | LIKE-fallback (повреждённый индекс) |
|---|---|---|
| `the` (текст «There he goes.», слова «the» нет) | **0 строк** — токен `there` ≠ `the` | **1 строка** — подстрока, ASCII-регистр складывается |
| `пехот` (текст «Пехотная дивизия») | **0 строк** | **0 строк** — LIKE складывает регистр **только для ASCII**; заглавная «П» не совпала со строчной «п» |
| `пехот` (текст «пехотный отряд») | — | **1 строка** — совпало (регистр совпадает) |
| `пехотная` (текст «Пехотная дивизия») | **1 строка** — целое слово, регистр складывается и для кириллицы | — |
| `юнит` (тексты «юнит стреляет», «Английские юниты идут») | **1 строка** — только точный токен `юнит`; токен `юниты` ≠ `юнит` | — |
| `английск` (текст «английские…») | **0 строк** — целое слово, не подстрока | — |
| `50%` (текст «50% done…») | — | **1 строка** — `%` сработал как wildcard |

**Ответы на вопросы ТЗ:**

- Почему «the» находит «There»: FTS нашёл в той строке **отдельное слово** `the`
  (в реальных текстах «the» встречается как слово постоянно); строка, где есть
  только «There» и нет отдельного «the», **не находится** (R2a). Это целословный,
  а не подстрочный матчинг.
- Почему «английск» и «пехот» не находят ничего: FTS-фраза сравнивается с
  **целыми токенами**, `английск` ≠ токен `английские`, `пехот` ≠ токен `пехотная`
  (R2b, R2e). При этом «юнит» находит строки с точным токеном `юнит` (R2d) —
  наблюдение Дмитрия целиком объясняется целословным матчингом.
- Гипотеза «SQLite LIKE регистронезависим только для ASCII» — **подтверждена для
  fallback-пути** (R2f–R2h: «the» находит «There», «пехот» не находит «Пехотная»
  с заглавной, но находит «пехотный» со строчной). Основной путь в реальной БД —
  FTS (он объясняет все наблюдения без fallback).
- Гипотеза «фильтрация по обрезанному/другому тексту» — **НЕ подтверждена**:
  фильтрация идёт в БД по полному тексту; обрезка `[:100]` — только отображение.
- Фильтр игнорирует Show: 120 записей в БД, «Show: 500» → показано **100**
  (жёсткий LIMIT 100 `concordance_search`); без фильтра те же 120 → показано 120.

### 0b. Устаревшее содержимое — ОСТАНОВКА (штатное поведение, изменений НЕТ)

Откуда Browse All берёт данные: `self.db_manager` → `DatabaseManager`
(`modules/database_manager.py`) → файл **`<user_data>/resources/supervertaler.db`**,
таблица `translation_units` (`Supervertaler.py:6188–6192`). Это **тот же** менеджер,
в который пишется подтверждение сегмента (`Supervertaler.py:28059` →
`save_segment_to_activated_tms` → `add_translation_unit`). Отдельного файла TM-БД нет.

Когда обновляется: только при **открытии диалога** (`load_initial_data` →
`refresh_browser`), по кнопке **Refresh**, после удаления записей (`delete_selected_entry`)
и после импорта TMX. Автообновления при показе вкладки нет; диалог **модальный**
(`dialog.exec()`), поэтому параллельных изменений «из другого места» в открытом
диалоге быть не может.

Пути удаления «базы» в коде:

1. **Настройки → TM-список → «🗑️ Delete TM»** (`Supervertaler.py:18722`) →
   `delete_tm(id, delete_entries=True)` — удаляет и записи (`DELETE FROM
   translation_units WHERE tm_id = ?`). НО: если этот DELETE падает (например,
   ошибка FTS-триггера на повреждённом индексе — документированный режим отказа
   в docstring `rebuild_fts_index`), записи **остаются в БД**, диалог показывает
   «Failed to delete TM».
2. **Удаление TMX-файла / источника импорта** — импортированные копии остаются в
   `supervertaler.db` навсегда: TM-БД существует **отдельно** от удалённого файла.
3. **«Clear all TM entries»** (двойное подтверждение, `Supervertaler.py:13962`) —
   очищает таблицу целиком через отдельное соединение.

**Вывод (остановка по ТЗ):** содержимое, пережившее перезапуск, физически лежит
в `supervertaler.db` — значит, удаление «базы» его не затронуло (путь 2, либо
неудавшийся путь 1). Это штатное поведение: TM-БД существует отдельно от
«удалённой базы». Пункт 0b не меняется; **задача 5 (свежесть при показе) снята**
по её оговорке «(если п.0b не остановил)». Проверка для Дмитрия — §7.6.

## 7. Ручная проверка для Дмитрия (D:\Supervertaler_clean или рабочая копия)

Каждый пункт: цель → шаги → ожидание → что считается провалом. ТМ с тестовыми
записями: подойдут и реальные; для кириллицы — хотя бы одна запись с Target
«Пехотная дивизия поддерживает фланг» и одна с «юнит стреляет».

### 7.1 Порядок по умолчанию
- Цель: Browse All открывается с ID по возрастанию и валидным индикатором.
- Шаги: TMs → Browse All (или Maintenance → вкладка Browse). Смотреть колонку ID.
- Ожидание: сверху наименьший ID, у заголовка ID стрелка вверх; клик по другому
  заголовку сортирует по нему; после Refresh — снова ID по возрастанию со стрелкой.
- Провал: сверху не наименьший ID, стрелки нет, или после Refresh порядок не вернулся к ID asc.

### 7.2 Фильтр
- Цель: подстрочный поиск без учёта регистра, включая кириллицу; Whole words; Search in.
- Шаги: в поле Filter ввести `пехот` → Enter. Затем кнопкой Clear очистить. Повторить:
  `ПЕХОТ` (найдёт то же); галка Whole words + `пехот` (не найдёт), Whole words +
  `пехотная` (найдёт); запрос `50%` или `_слово_`, если такие символы есть в записях
  (ищутся как обычные символы); «Search in: Target only» + слово, которое есть только
  в Source (не найдёт), «Source only» + то же слово (найдёт).
- Ожидание: каждая проверка даёт результат из §2 строк 3–4; после Clear — полная
  таблица без пустых строк и дублей ID.
- Провал: «пехот» при выключенной галке не находит «Пехотная…»; Clear оставляет
  пустые строки/дубли; режим Search in не влияет.

### 7.3 Раскладка
- Цель: глобальные действия внизу.
- Шаги: открыть Browse All; осмотреть верхнюю и нижнюю строки.
- Ожидание: верх — «Filter: [поле] [Filter] [Clear] Search in: [список] [Whole words]»;
  низ — «🗑️ Delete Selected … Show: N entries 🔄 Refresh Showing N entries».
- Провал: Show/Refresh остались наверху.

### 7.4 Полный текст
- Цель: длинные записи видны целиком, копирование не теряет хвост.
- Шаги: найти/создать запись с Source длиннее ~300 символов (например, вставить
  абзац); строка развернётся по высоте; навести курсор на ячейку — tooltip с полным
  текстом; выделить ячейку Source, скопировать (Ctrl+C — работает средствами Qt при
  выделенной ячейке через контекстное меню/сочетания среды) и вставить в блокнот.
- Ожидание: вставленный текст = полный исходник (не обрезан на 100-м символе).
- Провал: текст обрезан на 100 символах.

### 7.5 Клавиша Delete
- Цель: удаление выделенных строк клавишей Delete.
- Шаги: выделить 2–3 строки (Shift/Ctrl), нажать Delete на клавиатуре, когда курсор
  в таблице; в окне подтверждения проверить список ID; согласиться. Затем: поставить
  курсор в поле Filter, набрать слово, нажать Delete внутри поля.
- Ожидание: в таблице удаляются ровно строки из подтверждения (сверить тексты
  Source/Target удалённых записей!); Delete в поле редактирует текст запроса и ничего
  не удаляет из БД.
- Провал: удалились другие записи (сверять по тексту, не только по числу) или Delete
  в поле тоже удалил записи.

### 7.6 Свежесть данных (объяснение 0b, изменений нет)
- Цель: подтвердить, что «содержимое удалённой базы» — это записи в TM-БД,
  которые удаление TMX/неудавшееся удаление TM не затронуло.
- Шаги: (а) если удалялся TM из TM-списка — повторить удаление и смотреть лог
  приложения: строка «✓ Deleted TM (ID: …)» означает успех, «✗ Error deleting TM …»
  или окно «Failed to delete TM» — неудачу (записи остались); (б) удалить TMX-файл —
  записи останутся (штатно); (в) чтобы убрать оставшиеся записи, использовать Browse
  All → выделить → Delete, или Maintenance-очистку.
- Ожидание/провал: см. §1 0b. Если удаление TM из списка завершалось ошибкой —
  прислать лог, это отдельный баг (кандидат: повреждённый FTS-индекс).
