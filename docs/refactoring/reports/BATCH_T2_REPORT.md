## 1. Задача 1 — двойная запись в TM при подтверждении (коммит `ce1069bb`)

### 1.1 Как `update_status_icon` находит сегмент (проверка п.а промпта)

`update_status_icon(row, status)` берёт сегмент **по индексу строки**:
`segment = self.current_project.segments[row]` (`:37122`). Грид строится
`enumerate(self.current_project.segments)` (`load_segments_to_grid`, строка i = сегмент i),
ID-итем колонки 0 пишется из того же перечисления; сортировки (`apply_sort`) сортируют
список `segments` **на месте** и перезагружают грид целиком — соответствие «строка i =
segments[i]» сохраняется всегда. Все три сайта вызывают его со строкой, найденной по
ID того же сегмента (`_find_row_for_segment(segment.id)` / `current_row`), т.е. **сегмент тот же объект**.

Guard неявной записи: `not find_replace_active and status == 'confirmed' and segment.target.strip()`.
`find_replace_active` = True только пока открыт модальный диалог Find & Replace — в этот момент
подтверждения недостижимы. Пустой target отсекается так же, как явным вызовом. Т.е. **guard
срабатывает во всех достижимых состояниях явных вызовов**.

### 1.2 Выбранный вариант: (б) + локальное (в)

- **(б)** явные вызовы удалены на всех трёх сайтах:
  - `_confirm_current_row_segment` (:46849, Ctrl+Enter / Confirm & Next);
  - `confirm_selected_segments` (:47024, Confirm all; `tm_saved_count` теперь считается по
    условию неявной записи `segment.target.strip()` — результат лога «saved N to TM» тот же);
  - `_check_auto_confirm_100_percent` (:46745, авто-подтверждение 100%; успех-лог
    «Auto-confirmed and saved segment …» сохранён, теперь описывает неявную запись).
- Проверка п.г сьюта **нашла третье место двойной записи**: цепочка авто-подтверждения
  заканчивается `confirm_and_next_unconfirmed()`, который проходит
  `_confirm_current_row_segment()` по тому же сегменту — статус уже `confirmed`, и неявный
  guard `update_status_icon` срабатывает **второй раз** (на HEAD: 4 вызова на авто-подтверждение
  вместо 1). Для ровно одной записи применён **(в)** — параметр
  `update_status_icon(row, status, save_to_tm: bool = True)` (по умолчанию — прежнее поведение
  всех прочих вызовов), `_confirm_current_row_segment` передаёт
  `save_to_tm=(old_status != 'confirmed')`. Побочный эффект: повторный Ctrl+Enter на уже
  подтверждённом сегменте больше не пишет в TM (в режиме `all` раньше давал бы UNIQUE-ошибку);
  `record_undo_state` внутри `update_status_icon` выполняется как прежде (двойной undo-стейт
  существовал и до батча, не менялся).

## 3. Задача 3 — QuickEdit консоли (коммит `ffc7ac69`)

Новая модульная функция `disable_console_quickedit() -> bool` (`:54762`), вызов в `main()`
сразу после `_setup_diagnostic_log()` и до QApplication (`:55064`, прецедент стиля —
SetErrorMode-блок).

**Какой handle правится и почему:** входной буфер консоли — `GetStdHandle(STD_INPUT_HANDLE = -10)`.
По документации Console API `ENABLE_QUICK_EDIT_MODE (0x0040)` и `ENABLE_EXTENDED_FLAGS (0x0080)`
— флаги режима **входного** буфера (`GetConsoleMode`/`SetConsoleMode` на `-10`); пример
T-разведки C3 с `-10` был верен, выходной (`-11`) не при чём. Снятие с сохранением остальных
флагов: `mode = (mode | 0x0080) & ~0x0040`. Не-Windows / нет консоли (pythonw, redirect,
DETACHED_PROCESS) — тихий no-op (`False`): `GetStdHandle` возвращает NULL или
`GetConsoleMode` падает.

Тесты (`t2_console_quickedit_tests.py`, **10/0**):
- вызов в текущем процессе без исключений (в сьют-процессе консоли нет → False);
- ребёнок `DETACHED_PROCESS` (без консоли): `False`, `GetConsoleMode` недоступен, без исключений;
- ребёнок `CREATE_NEW_CONSOLE` (своя консоль): `True`, после вызова флаг 0x0040 снят,
  0x0080 установлен, режим 0x1B7 → 0x177;
- guard `sys.platform != 'win32'` — первым в функции (статически; на не-Windows хосте
  проверка кодовая, на win32-хосте не исполняется).
- Метод-замечание: `CREATE_NO_WINDOW` **не годится** для имитации «без консоли» — скрытая
  консоль существует, `GetConsoleMode` там успешен (показал первый прогон, 2 FAIL →
  исправлено на `DETACHED_PROCESS`; правился только тест, не продукт).

## 4. Задача 4 — faulthandler (коммит `7f8ea252`)

**Был ли включён:** нет — grep по монолиту до батча не находил `faulthandler` нигде в
продуктовом коде (только в сьютах `docs/refactoring/audits/*`).

**Куда пишет:** `_enable_faulthandler()` (`:54807`) включает
`faulthandler.enable(all_threads=True)` с файлом
`<user_data_path>/workbench/logs/supervertaler-fatal.log` — тот же механизм путей, что у
`_setup_diagnostic_log` (правило P1: внутри корня сборки, не в профиле пользователя, не в
реестре). Вызов в `main()` сразу после `_setup_diagnostic_log()`/`disable_console_quickedit()`
и до QApplication (`:55068`).

**Ограничение роста:** ротация «один предыдущий» при старте —
`supervertaler-fatal.log` → `supervertaler-fatal-previous.log` (предыдущая копия затирается),
новый открывается на запись (`'w'`); хранится не более 2 файлов (≈ размеры трассировок,
килобайты). Файл открыт через модульную переменную `_fault_log_file` и остаётся открытым всю
жизнь процесса. Ошибка открытия (нет прав, путь упёрся в существующий файл) — `try/except`,
возвращается `None`, приложение стартует без faulthandler-журнала.

Тесты (`t2_faulthandler_tests.py`, **12/0**): ребёнок включает faulthandler реальной функцией
и падает access violation'ом (`ctypes.string_at(0)`, `SEM_NOGPFAULTERRORBOX` против WER-окна);
в логе «Windows fatal exception: access violation» + трассировка с файлом/строкой; маркер
«прошлого сеанса» уехал в `-previous.log`, новый лог чист; путь внутри изолированного
`SUPERVERTALER_DATA_ROOT`; невоспроизводимый путь — `None` без исключения. Байт-уровень:
в логе виден `File "ctypes\__init__.py", line 548 in string_at`.

## 8. Ручные тесты для Дмитрия (простым языком, файлы для подмены в D:\Supervertaler_clean)

**Общая подготовка для всех четырёх тестов:** скопировать `Supervertaler.py` из репозитория
(E:\Dev\SupervertalerPortable) в `D:\Supervertaler_clean\SupervertalerPortable\` с заменой,
запустить программу через `start.bat`. Модель — любая рабочая (например, index-nailong-9b
в LM Studio). Журнал открывается кнопкой 📋 Log под сеткой сегментов.

**T-T2a — одна запись в TM при подтверждении группы (обязательный).**
1. Цель: убедиться, что подтверждение сегментов пишет в TM один раз, а не два.
2. Шаги: импортировать простой txt (несколько строк), перевести 5–10 сегментов (Ctrl+T
   каждый), выделить их в сетке мышью (клик на первый, Shift+клик на последний), нажать
   Ctrl+Shift+Enter (Confirm all).
3. Ожидаемый результат: в журнале ОДНА сводная строка «💾 Saved segment to 1 TM(s) (overwrite) (xN)»
   (раньше сегментов было в 2 раза больше строк «Saved…»); открыть Resources → Translation
   Memories → TM Browser: записей ровно столько, сколько подтверждено сегментов, без дублей.
4. Что считается провалом: строк «Saved…» вдвое больше сегментов; в TM-браузере видны дубли.

**T-T2b — одиночное подтверждение (обязательный).**
1. Цель: то же для Ctrl+Enter и Confirm & Next.
2. Шаги: перевести один сегмент, нажать Ctrl+Enter; затем перевести следующий и нажать
   Ctrl+Shift+Enter (Confirm & Next, если назначено) — либо повторить Ctrl+Enter на
   следующем.
3. Ожидаемый результат: на каждый сегмент в журнале ОДНА строка «💾 Saved segment to 1 TM(s)…»;
   запись появилась в TM-браузере.
4. Провал: две строки «Saved…» на один сегмент.

**T-T2c — консоль не замерзает (обязательный).**
1. Цель: убедиться, что клик мышью в окно консоли больше не останавливает программу.

## 9. Риски и примечания

- **QuickEdit** касается только машин с консолью (запуск через `start.bat`/`run.cmd`);
  откат — удалить вызов `disable_console_quickedit()` из main() (одна строка).
- **faulthandler** пишет трассировку при нативных сбоях; журнал ~килобайты, ротация
  ограничивает след. Не влияет на работу приложения при отсутствии сбоев.
- Двойная undo-запись в `_confirm_current_row_segment` (record_undo_state дважды —
  собственный + внутри `update_status_icon`) существовала до батча и сохранена
  (вне скоупа, «заодно» правок нет).
- Дебаунс-сохранение набранного текста (`_handle_target_text_debounced_by_id`) может
  добавить в TM запись после подтверждения, если пользователь подтвердил в течение 1 с
  после набора — отдельный легитимный сценарий «набрал → подтвердил», не тронут.
