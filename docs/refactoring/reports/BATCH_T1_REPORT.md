## §4. Task 2 (разведка) — почему «saved 28 to TM», а «Saved segment to 1 TM(s)» ×56

**Цепочка подтверждения (номера строк — состояние после коммита 2):**

1. Batch translate → Confirm all → `confirm_selected_segments` (**:46966**).
2. На каждый сегмент цикла:
   - **:47003** `self.update_status_icon(row, 'confirmed')` → внутри `update_status_icon`
     (**:37080**) guard **:37096–37099**: `status == 'confirmed' and segment.target.strip()`
     → `save_segment_to_activated_tms(segment.source, segment.target)` — **ЗАПИСЬ №1** →
     в конце `save_segment_to_activated_tms` (**:28070–28072**) лог
     «💾 Saved segment to {saved_count} TM(s){mode_note}» — **СТРОКА ЛОГА №1**;
   - **:47008** явный `self.save_segment_to_activated_tms(segment.source, segment.target)` —
     **ЗАПИСЬ №2** → **СТРОКА ЛОГА №2**.
3. Итог цикла: «✅ Confirmed 28 segment(s), saved {tm_saved_count} to TM» (:47016),
   где `tm_saved_count` = число сегментов (28).
4. Внутри каждого вызова: `tm_ids = get_writable_tm_ids(project_id)` — у Дмитрия 1 записываемая
   TM → `saved_count = 1` → каждая из 56 строк — «💾 Saved segment to **1** TM(s) (overwrite)»
   (mode_note «(overwrite)» = `tm_save_mode == 'latest'`, :28052).

**Вывод: 56 = 28 сегментов × 2 вызова.** Двойной вызов — то же, что в TBL1.0 было названо
«по случайности, а не по дизайну», но здесь подтверждён как **конкретный баг двойного вызова**:
`confirm_selected_segments` сохраняет сегмент в TM дважды — один раз через побочный эффект
`update_status_icon` (:47003), второй раз явно (:47008).

**Дубли в данных — есть или нет?**
- В режиме `latest` (у Дмитрия, «(overwrite)»): каждая запись = `DELETE` по
  (source_hash, tm_id) + `INSERT` той же пары (`database_manager.py`, add_translation_unit:
  overwrite-ветка). Второй вызов удаляет и вставляет то же самое — **итоговое содержимое БД
  идентично, дублей нет**, но работа (DELETE+INSERT+инвалидация кэша) выполняется дважды.
- В режиме `all` (overwrite=False): второй INSERT упал бы на констрейнте
  **`UNIQUE(source_hash, target_text, tm_id)`** (translation_units, database_manager.py:265) →
  «⚠️ Could not save to TM '…': …» и `saved_count = 0` → строки «Saved segment…» не печатаются.
  Дублей нет и здесь, но лог был бы зашумлён предупреждениями.
- То же в режиме `latest` при 2+ записываемых TM: «to 2 TM(s)» ×56.

**Статус: баг (лишняя работа + вводящий в заблуждение лог), данные не портятся.** Тот же
паттерн «update_status_icon + явный вызов» есть ещё в одном месте — авто-подтверждение 100%
TM-совпадения (~:46860–46868: `update_status_icon(row,'confirmed')` + явный
`save_segment_to_activated_tms` + свой лог) — **не правилось** (не входит в задачу; кандидат
на тот же микрофикс по вердикту). Минимальный кандидат правки (НЕ применён): удалить явный
вызов :47008 (и пару в авто-подтверждении) — guard в `update_status_icon` уже пишет в TM.

## §5. Task 3 (разведка) — две тонкие полоски под тулбаром редактора

**Что физически находится под тулбаром (проверено кодом + offscreen-пробой дерева виджетов):**

- Ряд «Status | 🧪 Preview Prompts (:24400) | 🏷️ AutoTagger (:24406) | | 📋 Log (:24419) | …
  ✓ Confirm && Next» — это `toolbar` QWidget (**:24289**), добавленный **последним** элементом
  в `grid_layout` контейнера `grid_container` (**:24434**). Layout `grid_container`:
  `[home_warning, QTableWidget, toolbar]` — **ничего после тулбара внутри контейнера нет**
  (проба: `probe/toolbar_probe.py`, offscreen, read-only).
- Ниже контейнера — вертикальный QSplitter `left_vertical_splitter` (**:23953**, handle 8px,
  :24639) с двумя панелями: `[grid_container, bottom_tabs]` (:24633–24634, по умолчанию
  «под сеткой», sizes [600, 200]). `bottom_tabs` (QTabWidget, **:24444**) = вкладки
  🔍 TermLens + ⚡ QuickTrans — «under-grid dock».
- Показ/скрытие дока — `set_termlens_position` (**:35633**): `None` → `tabs.setVisible(False)`;
  при старте восстанавливается из настройки `termlens_under_grid_visible`
  (**:6311–6320**, по умолчанию **False** = док скрыт).
- Batch-translate «информация о ходе перевода» — это **`LiveProgressDialog`**
  (modules/dialogs/live_progress.py:10): модальный QDialog 800×600 (`dialog.exec()`,
  :50539-область), **НЕ встроен** в главное окно. Прогресс-бары в главном окне: единственный
  QProgressBar принадлежит TMManagerDialog (не виден); видимых виджетов с высотой ≤6px нет
  (проба).

**Кандидаты на «две тонкие полоски» (по убыванию вероятности):**

1. **Under-grid dock, сжатый сплиттером до минимума** — единственный реальный виджет
   непосредственно под тулбаром. При сжатии QTabWidget остаётся = полоска панели вкладок
   (у TermLens/QuickTrans ≈ 30px) + 1–2px рамка страницы — визуально «две тонкие
   горизонтальные полоски». `setChildrenCollapsible(False)` (:24640) не даёт 0, но не
   мешает минимуму. Триггер: вертикальному сплиттеру не хватает высоты — например, после
   пакетного прогона строки стали выше (`auto_resize_rows` в `handle_translation_complete`,
   :50489-область) и минимум сетки вырос; **sizes [600, 200] повторно НИКТО не выставляет**
   (только при конструировании :24636 и в `set_termlens_position`) — поэтому сжатое
   состояние **сохраняется** до ручного перетаскивания или переключения дока через
   View ▸ TermLens / QuickTrans panel (:8190–8199). «Почему на третьем прогоне» — из кода
   детерминированно не выводится (зависит от геометрии окна и высоты строк в тот момент);
   механизм «сжали и не восстановили» кодом подтверждается, конкретный третий прогон —
   гипотеза, помечена как требующая GUI-воспроизведения.
2. **Артефакт отрисовки закрывающегося модального диалога** — на третьем прогоне модальный
   LiveProgressDialog закрылся на фоне тяжёлой перерисовки (`auto_resize_rows` по всем
   строкам) — остаточные линии рамки. Отличить просто: такой артефакт исчезает при первой
   же перерисовке (клик/изменение размера окна), сжатый док — нет.

**Связь с «🪟 Log window detached» / кнопкой «Log» — в коде НЕТ.** `detach_log_window`
(:10524–10536) только создаёт отдельное окно `DetachedLogWindow` (modules/dialogs/detached_log.py)
и пишет лог; сплиттер/док он не трогает. Кнопка «📋 Log» в тулбаре добавляется **безусловно при
старте** (:24419–24422) — она не «появилась» после отделения, Дмитрий мог просто заметить её
рядом с полосками; то же действие доступно и через Tools/View ▸ «📋 Log Window…» (:8277),
а настройка `auto_open_log` (:6288) сама открывает окно лога при старте.

**Минимальная правка-кандидат (одной строкой, НЕ применена):** в конце
`handle_translation_complete` (или в `update_progress_stats`) добавить
`if self.bottom_tabs.isVisible() and self.bottom_tabs.height() <= self.bottom_tabs.tabBar().height() + 2: self.left_vertical_splitter.setSizes([600, 200])` —
восстановить высоту дока, если он сжат до панели вкладок. **Риск: низкий** (только
перебалансировка сплиттера; данные и поведение не затрагиваются), но применение — только
после GUI-воспроизведения механизма (см. чек-лист для Дмитрия ниже).

**Чек-лист для Дмитрия (уточнение диагноза, без правок):** (а) исчезают ли полоски после
клика/изменения размера окна — если да, это артефакт отрисовки; (б) открыть View ▸
TermLens / QuickTrans panel → если док отрисуется нормально и полоски уйдут — это был
сжатый док; (в) если воспроизведётся устойчиво — сказать, какая вкладка дока была активна
(TermLens/QuickTrans) и была ли вкладка dock'а видима в первых двух прогонах.
