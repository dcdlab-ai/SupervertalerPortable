## s0. TL;DR — главные находки

1. **Кодировка установлена по первым байтам оригиналов:** оба txt — **UTF-16LE БЕЗ BOM**
   (первые байты `3C 00 55 00 4E 00…`, ни `FF FE`, ни `EF BB BF`). Чтения «в UTF-8» —
   артефакт перекодировки в чате. EOL — CRLF (по 932 в обоих файлах).
2. **Все 12 чисел координатора подтверждены точно, без расхождений:** 907 абзацев;
   32 783 тега тела; cNoBreak 27 794 тега (= **4611 пар** «открытие/закрытие»);
   U+00AD 259; U+2011 23; NBSP 0; CharStyle Bold 213 / Italic 6 / BoldItalic 4;
   myHorizontalScaleForEmDashSpaceBefore/After 167/168 при 168 тире.
3. **Форма «Abbreviated» — это ровно та же последовательность тегов с короткими именами:**
   потоки тегов обоих файлов равны по длине (32 811), отображение имён взаимно однозначное
   (41 пара, таблица в s3.5), а текст без тегов **побайтово совпадает** (207 752 символа в обеих формах).
4. **Гипотеза «cNoBreak и myHorizontalScale* идут от GrepStyle в стилях абзацев» ОПРОВЕРГНУТА**
   (проверка по IDML, s4.4): во всех стилях абзацев `EmptyGrepStyles="true"`, кроме
   `mainnumber--a)` (run-in GREP для цифр нумерации). Реальный источник — **локальное
   форматирование потока**: `NoBreak="true"` на CharacterStyleRange (ровно **4611 = 4611** пар
   cNoBreak) и символьные стили myHorizontalScale*, применённые в тексте (167/168 — точное совпадение).
5. **pRunInStyles (жирный лид до двоеточия) восстанавливается из определения стиля** — и из
   Tagged Text (`pRunInStyles:BoldItalic\,\:\,1\,0\;` в DefineParaStyle), и из IDML
   (`AllNestedStyles`: стиль + разделитель + повтор + Inclusive). В теле экспорта жирный лид
   тегами НЕ помечен — он применяется стилем при вёрстке (s4.3).
6. **IDML ≠ состояние Tagged Text по структуре абзацев:** главный рассказ IDML (DOM 21.5 =
   InDesign 2026) содержит 527 абзацев, экспорт 16.4 — 907 (совпадают только «особые» стили:
   H2 46=46, DesignNote 35=35, PlayNote 30=30, исключение 31=31, HistoricalNote 13=13;
   «текстовые» стили различаются вдвое: main 418 против 204+215, mainbullet 122 против 43).
   Инлайн-шум при этом идентичен (4611 NoBreak; 167/168 myHS). **Открытый вопрос координатору** —
   какая ревизия первична (s9).
7. **В программе сейчас нет ничего про InDesign Tagged Text** (`UNICODE-WIN`, `ParaStyle:` —
   ноль вхождений в репозитории); IDML импортируется/экспортируется через Okapi sidecar.
   Импорт/экспорт Tagged Text — новые хендлеры по образцу `import_simple_txt`/`export_simple_txt`.
8. **Выделения `**жирный**`/`*курсив*` в md сегодня — литеральные символы** (s6): не
   конвертируются ни во что при импорте, не защищаются при сегментации предложений (пара
   `**` может разорваться по границе сегментов), в docx идут как текст звёздочек. Рекомендация:
   для пути Tagged Text использовать существующие инлайн-теги `<b>/<i>/<bi>`; для md —
   отдельное решение (s6.3).

## s4. Часть B — аналитика

### s4.1 (а) Смысловые теги против шума вёрстки; правило «сырого» текста

Смысл в «сыром» тексте несут только: **стиль абзаца**, **CharStyle Bold/Italic/BoldItalic**
(+ редкие локальные cTypeface/cSize — s4.2), **принудительный перенос строки** (одиночный LF
внутри абзаца, 25 шт.), и **метки-заполнители нумерации** (numCFPrevious — сброс счётчика,
10 шт.). Всё остальное — следствие автоматики вёрстки.

| Тег | Значения в образце | Действие при импорте «сырого» текста |
|---|---|---|
| `ParaStyle/ps:` | имена 14 стилей | → **роль абзаца** (таблица соответствий, s5.1); счётчик в инвентаре |
| `CharStyle/cstyle:` | Bold 213, Italic 6, BoldItalic 4, main 9, myHS 335 | Bold/Italic/BoldItalic → **инлайн-теги** `<b>/<i>/<bi>` (или md-разметка — решение s6.3); main/myHS → снять, посчитать |
| `cNoBreak/cnb` | 4611 пар вокруг пробелов (3517), тире (165), «не м/не п/…» (словосочетания) | **снять** (шум вёрстки); посчитать в «что снято» |
| `cLeading/cl`, `cPosition/cp`, `cSize/cs`, `cTypeface/ct`, `cColor/cc`, `cFont/cf`, `cLanguage/clang` | локальные оверрайды (межстрочное, индексы, кегль, начертание, цвет) | cTypeface/cSize/cColor — распознать «локальный Bold» (s4.2), иначе **снять**; остальные — снять |
| `pDesired/Max/MinWordSpace/Letterspace/GlyphScale` | по 84 (вёрсточная подгонка) | **снять** |
| `pSameParaSpacing`, `pSpaceAfter/Before`, `pLeftIndent`, `pTextAlignment`, `pGridAlign`, `pBorder*`, `pShading*`, `pKeepLines`, `pHyphenate*` | сбросы/локальные абзацные оверрайды | **снять** (оформление должно жить в стиле целевого документа) |
| `cLigatures`, `cOTFContAlt` | по 16 | **снять** |
| `numCFPrevious` | 10 (продолжение нумерации) | учесть при роли «нумерованный список» (или снять с пометкой) |
| теги-сбросы с пустым значением (`<pLeftIndent:>`, `<CharStyle:>`, `<cNoBreak:>`) | ~14 тыс. | **игнорировать** (это закрывающие/сбросы) |

| одиночный LF в тексте | 25 | **сохранить** как принудительный перенос внутри сегмента |
| `<0x…>`-теги | 0 | (правило на будущее: якорные объекты — предупреждение «объект потерян», счётчик) |

### s4.2 (б) «Заголовки из main + локальный Bold + cSize»

Абзацы `ParaStyle:main` с локальным оформлением: **196 с CharStyle:Bold** (113 «чистый Bold»,
81 «Bold + cTypeface», 2 «Bold + cSize + cTypeface»), **7 с cSize** (5 без Bold, 2 с Bold+cTypeface),
61 с одним cTypeface. Примеры: «GBA: Хотя это не слишком сложная игра…», «Помните: Всегда следите
за флангами.», «Каждая игра Great Battles of Alexander содержит:».

Отличать «заголовок-подделку» от обычного выделения предлагается по признакам, в порядке силы:
(1) `CharStyle:Bold`/локальный Bold занимает **префикс абзаца до двоеточия** → это лид (run-in),
как у стилей mainbold/DesignNote, а НЕ заголовок; (2) Bold на весь абзац → кандидат в подзаголовок;
(3) cSize больше базового 10 pt (в образце 7 абзацев с cSize) → кандидат в заголовок. В образце
почти все 196 — лиды-выделения, а не заголовки; настоящие заголовки имеют стили H1/H2/H3.
Правило для инвентаря: показывать пользователю строку «main + локальный Bold: N абзацев, из них
лид до двоеточия: M» и позволить назначить роль (по умолчанию — «p, выделение сохранить»).

### s4.3 (в) pRunInStyles (жирный лид до двоеточия) — да, восстанавливается

Определение стиля несёт всё: `pRunInStyles:BoldItalic\,\:\,1\,0\;` = 4 поля
`<симв.стиль>\<разделитель>\<повтор>\<inclusive>` — подтверждено IDML-полем `AllNestedStyles`
(DesignNote/PlayNote/HistoricalNote/Example/исключение: BoldItalic + «:» + 1 + false;

## s5. Часть C — дизайн (без реализации)

### s5.1. Импорт Tagged Text → md/сегменты

**Двухфазный процесс.**

Фаза 1 — разбор + инвентаризация (без вопросов пользователю):
* токенизатор (образец — `i0_tagged_text_audit.py`, переносится в `modules/tagged_text/parser.py`);
  читает обе формы: сокращённые имена нормализуются к полным по статической таблице (s3.5 — она
  конечна и определяется InDesign, не документом); \-экранирование, вложенные `<>` заголовка;
* авто-определение кодировки: BOM → UTF-16LE/UTF-8; без BOM — `3C 00`/`00 3C` → UTF-16LE/BE, иначе UTF-8;
* абзац = кусок между CRLF; стиль = первый `ParaStyle` в куске; сбросы до него игнорируются;
  одиночный LF — принудительный перенос (сохраняется в тексте сегмента);
* инвентаризация: стили абзацев (имя, число, пример-абзац до 80 симв.), симв. стили (имя, число),
  локальные оверрайды cTypeface/cSize (группировка «Bold-подобные»), pRunInStyles из определений,
  bnListType (маркированный/нумерованный), счётчики всех снятых тегов.

Фаза 2 — назначение ролей (диалог):
* пользователю показывается инвентарь; каждому стилю абзаца назначается роль из словаря (s5.2);
  разумные дефолты по именам-эвристикам (H1→h1, main→p, mainbullet→li, mainnumbers→li_n,
  DesignNote/PlayNote/HistoricalNote→note, Example→example, исключение→p), всё правится;
* симв. стилям: Bold/Italic/BoldItalic → теги (дефолт), остальные — «снять/сохранить как есть»;
* сохранение назначений: **настраиваемая таблица «имя стиля → роль»** в `settings.json`
  (ключ `tagged_text_style_maps`, структура по образцу `segmentation_rules`); при следующем
  импорте из той же серии маппинг подставляется автоматически, новые стили попадают в диалог.

**Отчёт «что снято»** (защита от потерь): таблица «тег → сколько снято» + инвентарь сохранённого;
показывается перед созданием проекта и кладётся в лог проекта. Сверка: снято + сохранено =
общее число тегов файла.

**Неизвестные теги**: политика — по умолчанию «снять и посчитать» (строка «неизвестные: N —
имена»), чекбокс «Строгий режим» (остановить импорт со списком). Текст при этом не теряется никогда.

**Выход**: проект сегментов напрямую (рекомендуется): сегменты с `paragraph_id` (группировка),
`style` = роль, `type` = heading/list_item/para, текст — «сырой» без тегов вёрстки; далее штатная
сегментация по предложениям. md-выгрузка — опционально тем же конвертером (роли спецблоков —
через HTML-комментарии, s5.2).

### s5.2. Экспорт сегментов/md → Tagged Text

* **Словарь ролей** (HTML-подобный, расширяемый): `h1` (глава), `h2` (раздел), `h3` (подзаголовок),
  `p`, `li` (маркированный), `li_n` (нумерованный), `img` (метка изображения), `note`
  (плашка-примечание), `example` (пример). Спецблоки, которых нет в md (примечания, примеры):
  хранить роль в поле `Segment.style` проекта; в md-экспорте помечать HTML-комментарием перед
  абзацем `<!-- role:note -->` (переживает строковый круг, не виден в рендере; альтернатива —
  pandoc-фенсы `::: {.note}` — тяжелее, не рекомендую).
* **Таблица «роль → имя стиля InDesign»**: JSON в data root, один файл на серию
  (`<data_root>\mapping\<серия>.tagmap.json`), по умолчанию имена = ролям; редактируется в UI (I3).
* **Форма Verbose** (полные имена тегов — надёжнее для отладки и не требует обратной таблицы).
  Кодировка: дефолт **UTF-16LE + BOM**; вариант UTF-8 (с BOM; образцы Dmitry без BOM —
  InDesign 2021 определяет и так, но BOM снимает двусмысленность). EOL — CRLF.
* **Заголовок**: `<UNICODE-WIN>` + `<Version:…><FeatureSet:InDesign-Roman>` (ColorTable — только
  если экспортируются цвета). **Define*Style — не писать**: стили создаёт InDesign по именам
  при помещении (проверит T-I0), оформление несут стили целевого шаблона; это же делает файл
  переносимым между сериями.
* **Экранирование в тексте**: `\` → `\\`, `<` → `\<`, `>` → `\>` (в теле `>` безопасен, но
  экранируем для симметрии), `;` в значениях тегов — `\;` (в тексте не требуется). Принудительный
  перенос — `\n` (0x0A), абзац — CRLF.
* **Инлайн-теги** `<b>/<i>/<bi>` → `<CharStyle:Bold>/<CharStyle:Italic>/<CharStyle:BoldItalic>` …
  `<CharStyle:>`; `<li-b>/<li-o>` → стиль роли `li`/`li_n`.
* **Шум вёрстки НЕ писать** (cNoBreak, межсловные интервалы и пр.) — по данным s4.4 он
  воспроизводится автоматикой целевого документа (скрипты вёрстки; в предоставленном документе
  GREP-стилей нет — T-I0 проверит, сработает ли GREP целевого шаблона; если нет — шум вернётся
  при прогоне вёрсточных скриптов Dmitry).
* **Картинки**: абзац стиля роли `img` с меткой **дословно как в md**: `![alt](путь)`, экранированный.
  Пути — относительные, `images/` рядом с экспортом; программа при экспорте копирует файлы
  по путям меток в `<экспорт>\images\`. Потребление на стороне вёрстки (оценки, реализация — не в I-серии
  без отдельного решения): (1) вручную по меткам — 0 работы, риск опечаток; (2) **JSX-скрипт**
  (найти абзацы стиля img, спарсить метку, Place по якорю, удалить абзац-метку) — ~1–2 дня,
  средний риск, стандартная механика InDesign-скриптинга; (3) IDML-генерация — запасной вариант,
  недели работы, высокий риск совместимости — не рекомендован.
* **Что экспорт НЕ переносит** (и как это решается на стороне вёрстки): подписи к картам
  (живут отдельными рассказами вёрстки), колонтитулы/нумерацию (мастер-шаблоны), заливку/рамки
  плашек как свойства (восстанавливаются стилями целевого шаблона — имена в таблице маппинга),
  якорные картинки (метки img + JSX), локальные оверрайды (регенерируются автоматикой).
* **Переназначение стилей в InDesign после импорта**: штатный приём — в панели «Стили абзацев»
  удалить стиль с заменой («Удалить стиль…» → выбрать заменяющий) — все абзацы переключаются
  на целевой стиль; либо Alt-клик по стилю (переопределить). Включить в инструкцию T-I0.
* **md-таблицы → InDesign**: риск. Tagged Text таблиц не описывает (в образце их нет); вариант —
  экспортировать ячейки как абзацы роли `table_cell` с комментарием-заголовком и собирать
  вёрсткой вручную. Предлагаю: в I1/I2 таблицы помечать ролью `table` и писать текст ячеек
  построчно с предупреждением; автоматическая сборка таблиц — отдельное решение после замера
  реальных данных.

### s5.3. Развилка «каркас»: экспорт с нуля vs подстановка в экспорт вёрстки

* **A. Экспорт с нуля** (наши роли → стили целевого шаблона): чисто, но документ вёрстки
  придётся пересобирать (фреймы, развороты, картинки), все локальные особенности теряются.
* **B. Подстановка перевода в готовый экспорт вёрстки** (абзац в абзац): берём Tagged Text,
  выгруженный самой вёрсткой, и заменяем текст абзацев переводом, сохраняя `ParaStyle` и
  CharStyle-теги. Сохраняет структуру 1:1.
* **Локальные оверрайды при смене длины текста**: cNoBreak-пробелы после предлогов и
  myHorizontalScale-пары вокруг тире «рассыпаются» при изменении числа слов/тире (167 пар
  привязаны к 168 тире; если перевод тире потерял — пары остаются висеть). Данные s4.4
  показывают, что это шум, регенерируемый автоматикой вёрстки, поэтому в режиме B предлагаю
  **снимать шум из каркаса** и подставлять чистый текст: остаются только `ParaStyle` + смысловые
  CharStyle. Тогда B фактически превращается в «экспорт с нуля, но со стилевыми именами
  готового макета» — оба режима унифицируются одним писателем.
* **Рекомендация**: режим B со снятием шума как основной для серии (перевод абзац-в-абзац в
  готовый экспорт вёрстки); контроль: число абзацев каркаса = числу абзацев проекта (группа
  `paragraph_id`), при расхождении — предупреждение и отчёт по номерам абзацев. Режим A —
  как fallback (новая книга без макета). Если позже выяснится, что автоматика вёрстки НЕ
  регенерирует шум — добавить опцию «сохранять cNoBreak каркаса» (дешёвое расширение).

## s6. Часть E — выделения в md (`**жирный**`, `*курсив*`, `***жирный курсив***`), read-only

1. **md-импорт**: остаются литеральными символами в тексте сегмента (docstring и диалог говорят
   это прямо; конвертации нет). Подсветка `**` в таблице — чисто визуальная (S.py:2986–3002).
2. **LLM**: специфического правила для `**/*` в промптах нет; действует только общая строка
   дефолтного промпта «Preserve all formatting, tags, and placeholders exactly as they appear»
   (`unified_prompt_library.py:885`). Числовые теги `<N>` защищены отдельным правилом (S.py:5645–5656),
   `**` — нет. Потери/ломаные пары не измерялись (вне I0), риск очевиден из конструкции.
3. **Сегментация**: `MarkdownSegmenter` защищает от разреза код, картинки, ссылки, URL, HTML-теги
   (`simple_segmenter.py:183–203`) — **но не `**`/`*`**: выделение, пересекающее границу
   предложений, рвётся на `**начало` и `конец**` в разных сегментах.
4. **Экспорт**: в docx конвертируются только `<b>-стиль` теги; литеральные `**` пишутся в docx
   как звёздочки; в txt/md-экспорт — как есть. Проверки целостности `**` на экспорте нет.
5. **Обратный путь Tagged Text → md**: CharStyle Bold/Italic/BoldItalic → `**/*/`***` —
   тривиальный писатель, но только если выбран вариант «литералы».

### s6.1. Таблица вариантов хранения

|---|---|---|---|
| **Литералы `**`** (статус-кво для md) | нулевая работа; md-круг байт-в-байт; ничего не ломает | LLM не защищены (нет правила в промпте); разрыв пар при сегментации; docx-экспорт теряет форматирование; нет валидации | 0 |
| **Инлайн-теги `<b>/<i>/<bi>`** | вся существующая машинерия: промпт-правила «CRITICAL: TAG PRESERVATION», AutoTagger + `validate_tag_transfer`, предупреждение о потерянных тегах, docx-экспорт в реальные runs; Tagged Text экспорт отображается 1:1 в CharStyle | нужен конвертер `**`↔теги при импорте/экспорте md; теги видны в тексте сегмента (уже привычно по docx); помечать в сегментере как защищаемые (HTML-теги уже в списке защиты) | ~1–1.5 дня (конвертер + правило сегментера + тесты) |
| **Атрибуты (диапазоны форматирования отдельно от текста)** | чистая модель; текст для LLM вообще без разметки | большой рефакторинг Segment, сетки, редакторов, всех экспортов; против текущей архитектуры («теги — литеральные подстроки») | недели; не рекомендую в рамках I-серии |

### s6.2. Рекомендация (решение — отдельное)

Для **импорта Tagged Text**: CharStyle Bold/Italic/BoldItalic → `<b>/<i>/<bi>` сразу при разборе
(вариант 2) — переиспользует защиту LLM, docx-экспорт и валидацию, и это естественное
представление для обратного экспорта. Для **md-пути** — оставить статус-кво (литералы) до
отдельного решения; если решат конвертировать — тот же конвертер `**`↔теги (работа уже сделана
в варианте 2), плюс правило сегментера. В обоих случаях: правило в батч-промпт про сохранение
разметки выделений при её наличии.
