## 1. Причина (разведка + воспроизведение, коммит 1)

Ручной тест TM1 показал: в TM Browser → Browse All ID в таблице не соответствует тексту строки
(дубли ID, ID одной записи меняется между обновлениями), а после «Delete Selected» исчезают не те
записи, что выделены. Числа в подтверждении и логе верны.

### 1.1 Код (БЕЗ правок на момент разведки)

* `modules/tm_manager_qt.py:634` — `self.browser_table.setSortingEnabled(True)` включается **один раз
  при построении вкладки** и остаётся включённым навсегда.
* `refresh_browser()` (было :777–818) заполняет таблицу при **включённой** сортировке:
  `setRowCount(len(entries))`, затем по строке 6 × `setItem(...)` со строковыми `QTableWidgetItem`.
  При включённой сортировке **каждый `setItem()` вызывает пересортировку** таблицы — строки уезжают
  на лету, ячейки одной записи расходятся по разным строкам отображения.
* `delete_selected_entry()` (после TM1) читает id из `item(row, 0).text()` колонки ID — в
  рассинхронизированной таблице это текст чужой записи.

### 1.2 Воспроизведение (recon-тест `tm1_1_recon_scramble_before.py`, offscreen, N=30)

Ключевой нюанс: **на свежем окне бага нет** — индикатор сортировки после построения невалиден
(`sortIndicatorSection()=6` при 6 колонках), пересортировка при заполнении не срабатывает
(сценарий A0: 0 рассинхронов). Баг воспроизводится после реального действия пользователя —
**клик по заголовку + Refresh**:

| Замер (сортировка по ID asc + Refresh) | Значение |
|---|---|
| Строк с чужим текстом (ID ≠ source/target строки) | **28 из 30** |
| Дубли ID в колонке ID | **9** |
| Повторный Refresh — рассинхрон ДРУГОЙ | 28 → **22** («ID меняется между обновлениями») |
| Пример | row 0: ID=1 показывает source-013; row 3: ID=11 показывает source-001 |
| Удаление: в выделенных строках показаны | src-019, src-007, src-018 |
| Удаление: реально исчезли из БД | src-001, src-011, src-014 (**не те!**) |

Проверены и другие колонки (пробник): сортировка по Source desc даёт целые строки-дубли (10 дублей
ID, внутренне согласованные), по ID asc — худший случай с рассинхроном внутри строки.

Сортировка по ID была ещё и **лексикографической** (текст «10» < «2»): порядок 1, 10, 11, …, 2.

## 2. Исправление (коммит 2, `modules/tm_manager_qt.py`)

Таблица «было / стало / причина»:

| Место | Было | Стало | Причина |
|---|---|---|---|
| Заполнение `refresh_browser()` | `setRowCount(n)` + `setItem()` при включённой сортировке | `setSortingEnabled(False)` + `setUpdatesEnabled(False)` + `clearContents()` + `setRowCount(n)`, заполнение, затем `setUpdatesEnabled(True)` и `setSortingEnabled(True)` ПОСЛЕ заполнения | пересортировка на лету разносила ячейки одной записи по разным строкам |
| Порядок сортировки по умолчанию | индикатор заголовка (невалиден на старте, до первого клика — без сортировки) | **не изменён**: индикатор сохраняется, при повторном включении сортировки применяется тот же индикатор | правило батча: порядок по умолчанию — TM2 |
| Колонка ID | `QTableWidgetItem(str(id))` — текст, лексикографическая сортировка | `Qt.ItemDataRole.DisplayRole = int(id)` — заголовок сортирует числово | 1, 10, 11, …, 2 вместо 1, 2, 3 |
| Ключ записи в таблице | только текст колонки ID | `Qt.ItemDataRole.UserRole` = id записи **в каждой ячейке строки** | ключ не должен зависеть ни от номера строки, ни от текста, ни от сортировки |
| `delete_selected_entry()` | id из `item(row, 0).text()` | id из `Qt.UserRole` ячейки ID (fallback на текст для ячеек до-конвенции) | после пересортировки пользователем текст/номер строки — не ключи БД |
| Окно подтверждения | «Delete N selected entries from TM …?» | + список ID: до 10 штук через запятую, дальше «… and K more»; английский через `self.tr()`; формат для нескольких TM — как в TM1 | требование задачи 2 |
| Транзакция удаления | pre-flush commit, пачки ≤500, один commit, полный rollback | **без изменений** | TM1 уже верно |

Не тронуто: фильтр, concordance-поиск, статистика, диалог редактирования, кнопки, лимит загрузки,
строка лога `TM Browser: deleted N entries from …`, один refresh после удаления.

`Showing N entries` — считается от числа загруженных записей, после фикса совпадает с реальным
числом непустых строк (проверено сценарием c).

## 8. Ручная проверка для Дмитрия (опционально, 2 минуты)

**T-TM1.1a. Таблица Browse All соответствует базе после сортировки**

1. Открыть программу → вкладка **TMs** → подвкладка **Browse All**.
2. Нажать на заголовок колонки **ID** (сортировка по возрастанию) → нажать **🔄 Refresh**.
3. Смотреть на колонку ID: числа идут по порядку 1, 2, 3, … (не 1, 10, 11, 2), и в каждой строке
   Source/Target — текст именно этой записи (ID не «прыгает» между обновлениями при повторном Refresh).
4. Неуспех: после Refresh в строке ID=1 чужой текст, или порядок 1, 10, 11, …, 2.

**T-TM1.1b. Удаление выделенного при сортировке**

1. Там же: отсортировать по любой колонке, выделить 2–3 строки (клик + Shift+клик, ещё одну Ctrl+кликом).
2. Нажать **🗑️ Delete Selected**: в окне подтверждения должен быть список ID (например
   «IDs: 3, 7, 12»); нажать Yes.
3. Открыть список снова: исчезли именно выделенные записи, остальные на месте.
4. Неуспех: список ID в подтверждении отсутствует, или исчезли другие записи.
