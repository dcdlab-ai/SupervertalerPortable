## 1. Где и как импортируется md/txt-файл

### 1.1 Точка входа и меню

* Пункт меню **Project → Import → Text/Markdown file** привязан к
  `import_txt_action.triggered.connect(self.import_simple_txt)` — `Supervertaler.py:7691`.
* Сам импорт — **`import_simple_txt()`**, `Supervertaler.py:29568–29931`.

### 1.2 Как режутся строки

1. Диалог выбора файла: `Text Files (*.txt *.md);;Markdown (*.md);;Plain Text (*.txt);;All Files (*.*)` (`:29577`).
2. Опции-диалог (не-модальный контекст, `QDialog.exec`): языковая пара (запоминается в
   `general_settings['last_import_source_lang'/'last_import_target_lang']`), чекбокс
   **«Split lines into sentences»** (`last_import_sentence_segment`), предупреждение про
   Markdown-синтаксис.
3. Чтение: `open(file_path, 'r', encoding='utf-8')` → **`f.readlines()`** — одна физическая
   строка файла = одна единица импорта (`:29735–29738`). При `UnicodeDecodeError` — повтор
   с `latin-1`, `cp1252`, `iso-8859-1` (`:29862–29870`).
4. Текст строки: `text = line.rstrip('\r\n')` (`:29745`, повтор `:29873`).

### 1.3 Как формируются Segment и где ставится paragraph_id

Два режима:

* **Без пословного разбиения (дефолт)** — `:29764–29771`:
  каждая строка → `Segment(id=len(segments)+1, source=text, target="", status="untranslated",
  type="para", paragraph_id=line_num, document_position=line_num)`.
  `paragraph_id` = **номер физической строки файла** (1-based, `enumerate(lines, 1)`).
* **«Split lines into sentences»** — `:29749–29762`: `self._make_sentence_segmenter(markdown=is_markdown)`
  → `segment_with_separators(text)`; каждому предложению — свой `Segment` с тем же
  `paragraph_id=line_num`, `document_position=line_num`, `join_before=separator`
  (склейка при экспорте через `modules/simple_segmenter.join_segments`).
* **Пустая строка** → пустой сегмент, комментарий `:29743` — «hidden in grid, preserved for
  export» (структура документа сохраняется).

Ключевое для TBL1: **никакого распознавания таблиц нет.** Строка
`|**FRANCO-SCOTS**|**ENGLISH**|` и строка-разделитель `|---|---|` попадают в сегменты
как обычный текст (`type="para"`), синтаксис md сохраняется «как есть»
(docstring `:29569–29575`: «Markdown-файлы импортируются как есть (синтаксис
сохраняется для обратного круга)»). Подсветка — только синтаксическая:
`TagHighlighter._is_markdown_project = is_markdown` (`:29788`; флаг `:2751`,
подсветка `:2910–2911`, правила `:2975`).

### 1.4 Дублирование кода построения сегментов (риск для TBL1)

Логика «строки → сегменты» записана **дважды**: основной путь (`:29749–29771`) и копия
в ветке fallback-кодировок `UnicodeDecodeError` (`:29873–29910`). Любая таблиц-логика
TBL1 должна либо вноситься в оба места, либо (правильно) выноситься в общую функцию —
иначе импорт latin-1/cp1252-файла потеряет ячейки. Отдельно: fallback-ветка создаёт
проект **без** `_apply_reimport_settings` и части финализации — historic-поведение,
не трогать вне скоупа.

### 1.5 Прочее после импорта

`project.original_txt_path = file_path` (`:29784`), `project = Project(name="MD Import - …")`,
`_original_segment_order = segments.copy()`, `load_segments_to_grid()`,
`initialize_tm_database()` (`:29809`), `_clear_caches_after_import()`,
`_deactivate_all_resources_for_new_project()` (только для новых проектов), спелчек по

`_check_reimport_same_file` (`:40208`) по атрибутам
`['current_project.original_txt_path', 'current_document_path']`.

### 1.6 Где живут is_table_cell / table_info сегодня

Модель — `modules/models.py:112–145`, `Segment`:

* `:119` — `type: str = "para"` (допустим `table_cell`);
* `:133` — `is_table_cell: bool = False`;
* `:134` — `table_info: Optional[tuple] = None` — комментарий: «(индекс_таблицы, строка, ячейка)».

**Единственный источник реальных значений — legacy python-docx путь** DOCX-импорта
(`modules/docx_handler.py:450–461`): `ParagraphInfo(is_table_cell=True, table_index=table_idx,
row_index=row_idx, cell_index=cell_idx, …)`. Но актуальный DOCX-импорт идёт **только через
Okapi**, и там `para_info = None` — `Supervertaler.py:29358–29374`, комментарий прямо
говорит: «Okapi import: no per-paragraph metadata (table info, styles like Heading1) is
currently piped through». Преобразование `:29375–29396` читает `para_info.is_table_cell`
→ `table_info=(table_index, row_index, cell_index)`, но при `para_info=None` всегда
`is_table=False, table_info=None` (`:29419–29420`).

**Вывод: у всех новых проектов сейчас `is_table_cell=False` / `table_info=None`; поля —
инфраструктура без данных.** Достаточно ли тройки (таблица, строка, столбец): **да** для
адресации ячейки, **но** признака заголовка нет — для md-таблиц заголовок определяется
позицией (строка перед `|---|`), поэтому либо расширять `table_info` до 4-элементного
кортежа `(table_idx, row, col, is_header)`, либо кодировать заголовок через `type="table_cell"`
+ отдельное поле. Расширение кортежа не ломает существующих потребителей (см. ниже — все
сравнивают кортежи на равенство).

## 2. `<br>` — текущая обработка и что будет, если он останется

Постановка принята: `<br>` (артефакт PyMuPDF4LLM) — это перенос строки **текста в ячейке**,
а не разметка; сохранять не нужно, чистка — на этапе получения md из PDF (в docling его
нет). Правила разбора ячеек ничего с ним не делают. Зафиксировано в коде:

* **`modules/tagged_text/writer.py`** — единственное место, где `<br>` обрабатывается:
  docstring `:20` («`<br>` → одиночный LF»), правило `:101`; механика — `make_plain_processor` /
  `process_plain` (`:275–301`): при сборке Tagged Text `<br>` декодируется в **одиночный LF =
  принудительный перенос строки внутри абзаца** (InDesign interpretирует LF в тексте абзаца
  как hard return).
* Импорт md/txt (`import_simple_txt`), `modules/simple_segmenter.py`, подсветка — `<br>`
  **не обрабатывают нигде** (grep: 0 вхождений): он попадает в сегмент как обычный текст.
* **Следствие для ячейки**: если `<br>` останется в тексте ячейки, при экспорте Tagged Text
  он превратится в принудительный перенос строки внутри абзаца роли table_row — ожидаемое
  поведение, решение «оставить как есть» зафиксировано, правок не предлагается.
* Из тестов и рисков TBL1 всё про сохранение/преобразование `<br>` как разметки **убрано**
  (в настоящем отчёте не фигурирует).

## 3. Как ячейка должна жить в проекте (проектное предложение, на утверждение)

### 3.1 Поля

* `is_table_cell=True`, `table_info=(table_idx, row, col, is_header)` — расширение на 4-й
  элемент; все текущие потребители сравнивают кортеж на равенство, изменения не требуются.
  Альтернатива (не推荐): отдельное поле `is_table_header` — дороже по совместимости .svproj.
* `type="table_cell"` — тип уже упомянут в модели (`models.py:119`).
* `paragraph_id`: предлагается **глобальный сквозной счётчик логических строк-«событий»
  документа** (как сейчас `line_num`), т.е. все ячейки одной md-строки делят один
  `paragraph_id`. Это сохраняет инвариант `groupby(paragraph_id)` в экспорте (см. §4.2)
  и даёт склейку «в одну строку» бесплатно, НО склейка через `join_segments` соединит
  ячейки **пробелами, без `|`** — для pipe-строки этого мало (§4.3).
* `document_position` — тот же счётчик строк; порядок списка `project.segments` —
  построчный (row-major), ячейки одной строки подряд.
* `source` ячейки — **очищенный текст без pipe-обрамления** (`|` и внешние пробелы сняты),
  иначе цель «в TM не попадают строки с `|`» не достигается.

### 3.2 Строка-разделитель `|---|---|`

Сегментом быть не должна (сейчас она становится сегментом — это и есть жалоба из образца).
Вариант: не создавать сегмент, а число столбцов/факт разделителя хранить в структуре
таблицы (см. §4.3 — разделитель регенерируется при экспорте). Решение координатора;
альтернатива «пустой скрытый сегмент» сохранит счётчики, но замусорит грид и TM.

### 3.3 Грид

Сегодня спец-обработки ячеек нет (колонок/подсветки для таблиц не существует, есть только
markdown-подсветка `TagHighlighter`). Минимум для TBL1: **ничего не менять** — ячейка
выглядит как обычный сегмент. Опционально (отдельный подбатч): индикатор в колонке ID/статуса
(иконка «⊞»), тултип `table/row/col`, подсветка строки заголовка. Предлагаю перенести в
TBL1-«грид»-подбатч по желанию координатора, к импорту/экспорту не обязательно.

### 3.4 Контекст промта (соседние сегменты)

Блок контекста — `translate_current_segment`, `Supervertaler.py:48570–48602` (после C1
координаты сместились; в C1.0 было :48504–48531): N соседей (`general_prefs['surrounding_segments']`,
дефолт 5) **по порядку списка** `current_row ± N`, маркеры из `modules/prompt_markers`
(парные `>>> id. source <<< [TRANSLATE THIS]`, заголовок блока).

Для таблицы-по-ячейкам:

* соседние ячейки той же строки таблицы будут в контексте автоматически (построчный
  порядок) — **достаточно** как базовое решение;
* нюанс: source ячеек без `|` — модель не увидит, что это таблица (сейчас pipe-строка
  целиком несёт `|`-маркеры). Если потребуется, можно добавлять в блок контекста
  строку-родитель (собранную pipe-строку) для ячеек — **предложение, не решение**;
* эхо-детектор C1 (`looks_like_prompt_echo`) пропускает сегменты, у которых маркеры есть в
  source — на чистые ячейки влияет положительно (ложных `>>>` в ячейке меньше, чем в полной
  pipe-строке);
* замечание вне скоупа TBL1: контекст нарезается по `current_row ± N` без учёта `file_id` —
  в многофайловых проектах соседи могут быть из другого файла (существующее поведение,
  зафиксировано).

## 4. Обратная сборка: кто экспортирует по сегментам и что менять

### 4.1 Карта экспортёров

| Экспортёр | Точка | Источник строк | Таблицы |
|---|---|---|---|

| Tagged Text (InDesign) | `export_tagged_txt` `:30133`; `md_text='\n'.join(...)` `:30227`; `write_tagged_text` `modules/tagged_text/writer.py:437` | `_collect_translated_lines` + `_collect_source_lines` (эхо, C1) | pipe-строки → роль `table_row` (`mdparse.py:136–137`), разделители `\|---\|` **отбрасываются** (`:127–129`), ограды → table_row (`:102–118`); настоящие таблицы InDesign — TBL2 (writer docstring `:36–37`, эталон синтаксиса в I0-C) |

| DOCX | `export_document` `:11643` / `export_okapi_merge` `:28871` (Okapi merge по `okapi_tu_id`) | Okapi-конвейер | обратная запись в таблицы docx — только legacy `docx_handler` (`_find_table_cell_info`), к md-таблицам отношения не имеет |

### 4.2 `_collect_translated_lines` / `_collect_source_lines` (`:29933–29971`)

Общий источник строк для TXT/MD и Tagged Text (правило I2). Группировка:
`groupby(segments, key=paragraph_id)` → `join_segments([(text, join_before), …])`.
Два инварианта, важных для ячеек:

1. **Порядок**: `groupby` склеивает только подряд идущие сегменты с одинаковым
   `paragraph_id` — порядок списка `project.segments` обязан быть row-major по ячейкам.
2. **Склейка**: `join_segments` соединяет тексты сегментов одной группы — для ячеек
   надо соединять `| cell1 | cell2 |`, чего `join_segments` не умеет.

### 4.3 Что нужно, чтобы таблица из ячеек собиралась обратно в pipe-строки (первый шаг)

План первого шага — **прежний md-формат** (writer уже понимает `table_row`; настоящие
таблицы InDesign — TBL2):

* В `_collect_translated_lines` (и зеркально `_collect_source_lines`) — ветка: сегменты с
  `is_table_cell=True` группируются по `(table_info[0], table_info[1])` и собираются в
  строку `| a | b | c |` (обрамляющие `|` обязательны — иначе `mdparse` не даст роль
  `table_row`, см. `:136`: `'|' in stripped and stripped.startswith('|')`).
* Строка-разделитель **регенерируется** после строки заголовка (`is_header=True` первой
  таблицы): `|---|` × числу столбцов. Число столбцов = max col по строкам таблицы.
* Сегменты без таблицы — прежний путь (группировка по `paragraph_id`).
* Ничего менять в `writer.py`/`mdparse.py` **не требуется**: на вход снова приходят
  готовые pipe-строки. `<br>` внутри ячеек пройдёт как обычный текст → LF (§2).
* Место, куда поместить разбор/сборку: новый небольшой модуль (предложение:
  `modules/md_table_cells.py` — `parse_md_table_line`, `is_table_separator`,
  `build_pipe_row`, `build_separator_row`), переиспользуемый импортом и экспортом.
* TMX/Bilingual-MD не меняются: ячейка = отдельный TU/строка — это и есть цель (в TM
  попадает чистый текст ячейки без `|`, `<br>`, `**`).

## 5. Обратная совместимость

* **Старые .svproj**: `Segment.from_dict` (`models.py:255–259`) отбрасывает неизвестные
  поля → старые проекты без новых данных грузятся как раньше; строки-таблицы остаются
  строками (`is_table_cell=False`), экспорт по ним идёт прежним путём (`_collect_*`
  не увидит ячеек → прежняя группировка по `paragraph_id`). Байт-в-байт результат
  экспорта обязан совпасть (тест).
* **Новые поля в .svproj**: `to_dict = asdict` сериализует `table_info` автоматически.
  Нюанс: **JSON превращает кортеж в список** — после загрузки `table_info` будет `list`,
  не `tuple`. Равенство-сравнения (split/merge guard) кортеж↔список дадут False; код
  TBL1 обязан нормализовать (`tuple(seg.table_info)`) при использовании, либо хранить
  table_info списком изначально. Зафиксировано как обязательное требование к подбатчу
  импорта.
* **Старый экспорт**: TXT/MD/Tagged-Text/TMX на старых проектах не затрагиваются
  (ветка ячеек не срабатывает).
* **Пакетный перевод** (numbered map, `^(\d+)\.` `:5697+`) и одиночный — работают по
  сегментам одинаково для ячеек и строк; проверка регрессом.

## 6. Побочный вопрос (ТОЛЬКО диагностика): TM «project» + «✓ Added to TM»

Наблюдение Дмитрия: при переводе в логе подряд
`⚠️ Refusing to add TU: tm_id 'project' has no row in translation_memories (orphan write blocked)`
и `✓ Added to TM: …`.

### 6.1 Откуда предупреждение

Guard «phantom-TM write» v1.10.213: `modules/database_manager.py:1028–1034`
(`add_translation_unit`), проверка `_tm_id_exists` `:1077–1098` — `SELECT 1 FROM
translation_memories WHERE tm_id = ? OR CAST(id AS TEXT) = ?`.

### 6.2 Где живёт tm_id='project' и почему строки нет

* Вызов: `translate_current_segment` → `self.tm_database.add_to_project_tm(source, translation)`
  — `Supervertaler.py:48775` → `modules/translation_memory.py:173` →
  `add_entry(…, tm_id='project')` (`:150–170`).
* `'project'` — **легаси-конвенция**: комментарий в `translation_memory.py:130–132`:
  «Legacy 'project' and 'big_mama' TMs are no longer used. All TMs are now managed through
  TMMetadataManager and stored in translation_memories table». **Ни один путь кода не
  создаёт строку `translation_memories` с `tm_id='project'`** → guard отбивает запись всегда
  (не только «когда нет активных TM»). Это мёртвый legacy-путь записи.
* Второй такой же вызов: авто-вставка 100% TM-совпадения — `Supervertaler.py:48559`.

### 6.3 Сообщение «✓ Added to TM» — проверяет ли результат

**Нет.** `add_translation_unit` при отказе guard'а возвращает `None` (без исключения),
`add_entry` возвращаемое значение игнорирует, а вызывающий код `:48773–48779` печатает
`✓ Added to TM: …` **безусловно** сразу после вызова. Лог лжёт; рядом честное предупреждение
от guard'а — отсюда пара строк в логе.

### 6.4 «Добавление в TM только после подтверждения» — так ли в коде

В коде **две группы путей записи в TM**:

1. **Подтверждение (контракт)**: смена статуса на `confirmed` →
   `save_segment_to_activated_tms` — `Supervertaler.py:37045–37050` (определение `:27987`):
   пишет во все TM с флажком **Write** (`get_writable_tm_ids`), реальными tm_id; при
   отсутствии записываемых TM — честный лог «⚠️ No TMs with Write enabled». Это и есть
   «только после подтверждения».
2. **Черновик (легаси, фактически мёртвый)**: сразу после получения перевода, при
   `status="draft"` (`:48773` — до подтверждения), — `add_to_project_tm` (`:48775`) и
   авто-вставка 100%-совпадения (`:48559`). Оба пути **всегда** упираются в guard 'project'
   и ничего не пишут.

**Вывод для координатора**: фактическое поведение соответствует ожиданию Дмитрия
(в TM попадает только подтверждённое), **но по случайности** — из-за мёртвого legacy-пути,
а не по дизайну; при этом логи вводят в заблуждение. Риск: если в старой БД пользователя
сохранилась строка TM с `tm_id='project'` (миграция со старых версий), draft-путь начал бы
молча писать в неё до подтверждения. Кандидат на отдельный микробатч-чистку (убрать
`add_to_project_tm` из двух мест или заменить логом «будет сохранено в TM после
подтверждения» + выровнять «✓ Added to TM» с проверкой результата). **В TBL1 не включать**
— скоуп разведки не затрагивается; решение за координатором.

## 7. Оценка объёма, риски, разбиение на подбатчи, тесты

### 7.1 Оценка объёма

* Новый модуль `modules/md_table_cells.py` (разбор pipe-строки/разделителя, сборка строки
  из ячеек, регенерация разделителя): ~150–200 строк + тесты.
* `import_simple_txt`: факторизация двойного кода построения сегментов в одну функцию +
  таблиц-логика: монолит ±100–150 строк (частично компенсируется дедупликацией).
* `_collect_translated_lines`/`_collect_source_lines`: +30–60 строк на ветку ячеек
  (или общий helper в новом модуле).
* Грид: 0 (минимум) — 60 (опциональные индикаторы).
* `packaging_helper.py`: +1 модуль в importsmoke.
* Итого: один основной батч + опциональный грид; масштаб заметно меньше I2.

### 7.2 Предложение разбиения

* **TBL1.1 — импорт + модель**: `modules/md_table_cells.py` (парсер), дедупликация
  построения сегментов в `import_simple_txt`, раскладка по ячейкам
  (`table_info=(table_idx,row,col,is_header)`), разделитель — не сегмент; сохранение
  старого поведения при отключённом распознавании (флаг/настройка — решение координатора).
* **TBL1.2 — экспорт**: ветка ячеек в `_collect_translated_lines`/`_collect_source_lines`
  (сборка pipe-строк + регенерация `|---|`), TXT/MD и Tagged Text получают прежний md;
  грид без изменений. Включает регресс-тесты совместимости.
* **TBL1.3 — грид/контекст (опционально)**: индикатор ячейки/заголовка, тултип; (если
  решит координатор) pipe-строка-родитель в контексте промта.
* **TBL2** — настоящие таблицы InDesign (отдельная линия, не в TBL1).

### 7.3 Риски

1. **Двойной код построения сегментов** в `import_simple_txt` (§1.4) — если забыть
   fallback-ветку, таблицы теряются на не-UTF-8 файлах. Обязательная дедупликация.
2. **JSON tuple→list** для `table_info` после круга .svproj (§5) — сравнения и индексация;
   нормализация обязательна.
3. **Порядок groupby**: ячейки одной таблицы обязаны идти подряд в `project.segments`;
   любая будущая сортировка (по `id`, по статусу) может разбить таблицу — экспорт-ветка
   должна группировать по `table_info`, а не полагаться на соседство (сейчас `_collect_*`
   полагается на соседство через groupby — для ячеек заменить на явную группировку).
4. **Пакетный перевод**: ячейки попадают в numbered-map путь; пустые ячейки и ячейки из
   одних цифр/пунктуации — те же правила, что для строк (переводится/копируется) — покрыть
   тестами.
5. **Split/Merge внутри ячейки**: guard уже есть (`segment_split_merge.py:157–158`) —
   регресс-тест.
6. **Sentence-segmentation внутри ячейки**: сейчас опция режет строку на предложения;
   для ячеек решение координатора (рекомендация: выключать внутри таблиц, ячейка = сегмент).
7. **Пустые ячейки**: become empty segments (грид скрывает, экспорт должен выдать `| |`) —
   явно покрыть тестом.
8. **Многофайловые проекты**: `table_info` не содержит file — таблицы считаются в рамках
   файла; `file_id` различен, смешения не будет, но группировку экспорта делать по
   `(file_id, table_info)` для безопасности.

### 7.4 Список тестов (предложение)

Автоматические (офскрин, без полной инстанциации — стиль `c11_report_dialog_tests.py`):

1. Парсер: md с таблицей 2×2 + заголовок (образец из задания
   `|**FRANCO-SCOTS**|**ENGLISH**|`) → ячейки без `|`, `is_header` у первой строки,
   разделитель — не сегмент.
2. Обратная сборка: сегменты-ячейки → через `_collect_translated_lines` → pipe-строки;
   сравнение с исходной таблицей построчно (байт-в-байт).
3. Пустая ячейка → `| |` при экспорте; пустая строка вне таблицы → пустая строка.
4. Совместимость: сегменты-строки без `table_info` → прежний путь `_collect_*` (байт-в-байт
   регресс на фикстуре).
5. Круг .svproj: сохранить/загрузить проект с ячейками → `table_info` переживает JSON
   (нормализация tuple/list).
6. Split/merge guard: merge соседних ячеек запрещён, внутри одной ячейки разрешён.
7. Эхо-детектор: перевод ячейки с маркерами в source — детектор не срабатывает (регресс C1
   33/0 остаётся).
8. Writer-регресс: экспорт Tagged Text на собранных pipe-строках — роль `table_row`,
   разделители отброшены, предупреждения отчёта на месте (регресс I-сьютов).

Ручные (3–5, для Дмитрия):

* T-TBL1a: импорт тестового md с таблицей → в гриде каждая ячейка = отдельный сегмент,
  `|---|` не создала сегмент; лог «Loaded N segments» соответствует.
* T-TBL1b: перевод ячейки (Ctrl+T) → в TM не появляется строка с `|`.
* T-TBL1c: экспорт TXT/MD → таблица собрана обратно в pipe-строки, разделитель на месте.
* T-TBL1d: экспорт Tagged Text → отчёт показывает table_row, таблица в InDesign —
  абзацы (как сейчас), перевод на месте.
* T-TBL1e: открыть старый проект со строкой-сегментом → поведение прежнее.
