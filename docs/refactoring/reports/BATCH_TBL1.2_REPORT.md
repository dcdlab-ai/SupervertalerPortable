### 4. Экспорт: как определяется заголовок и число столбцов разделителя; блок без заголовка

Группировка — `_group_export_items` (новый staticmethod SupervertalerQt): сегменты с
`table_info` **длины 4** (формат TBL1.2) группируются ЯВНО по ключу
`(file_id, table_info[0], table_info[1])` — без опоры на соседство в списке сегментов
(сортировка грида не ломает сборку; порядок строк = порядок первого появления группы).
Заголовок = `table_info[3]` (is_header) — все ячейки строки разделяют его. Разделитель
`build_table_separator(len(ячеек строки заголовка))` вставляется сразу после строки
заголовка; у блока **без заголовка разделителя нет** — не выдумывается. Прежний формат
`table_info` (legacy docx, кортеж длины 3) и обычные сегменты идут прежним путём
paragraph_id + join_segments (не тронут). Текст ячейки — по тому же правилу пустого
перевода, что у обычных сегментов: `target` непустой → `target`; иначе `source` при
`use_source_fallback`; иначе `""`. Строки таблицы идут подряд через `\n`, вокруг таблицы —
как у обычных абзацев. `_collect_source_lines` собирает те же md-строки из `source` ячеек
(выравнивание 1:1 для детектора эха C1 сохранено; разделитель после заголовка тоже, чтобы
нумерация строк совпадала).

### 5. Поведение mdparse на ячейке с «\|»

Не ломается. Строка «| … \| … |» начинается с «|» → блок `table_row`
(`modules/tagged_text/mdparse.py:135-137`); `\|` — просто текст внутри блока, разбора на
ячейки mdparse не выполняет. Отдельный случай: строка-разделитель «|---|---|» (в т.ч.
регенерированная экспортом) отбрасывается раньше (mdparse.py:129, `table_separators_dropped`).
Проверено и сьютом (секции E2/J), и в i2 B5: полный GUI-экспорт с ячейкой, содержащей
литеральный «\|» (т.е. «\\|» на выходе escape_cell), проходит тот же writer-пайплайн без
новых предупреждений (J4: warnings 0). mdparse не правился.

## §5. i2 = 38/1: B9 (найдено, доказано, сьют НЕ правился — решение за координатором)

**B9 «pymupdf: GUI-экспорт == CLI-выход с картой MyMap (байт-в-байт)»** больше не может
выполняться байт-в-байт на образце с таблицами. Причина — решение 4 вердикта TBL1.0 («формат
строки "| a | b |"»): импорт нормализует ячейки (trim), экспорт собирает строку канонически
(`build_table_row`), а CLI-путь (`python -m modules.tagged_text` по исходному файлу) пропускает
исходную строку как есть. В образце PyMuPDF4LLM ячейки без паддинга («|**FRANCO-SCOTS**|**ENGLISH**|»),
в docling — с паддингом; поэтому **B5 (docling) PASS**, **B9 (pymupdf) FAIL**.

Доказательство: diff фактических выходов (`pymupdf_gui.tagged.txt` vs `pymupdf_cli.tagged.txt`):
102/102 строк у обоих; ВСЕ отличия — только пробелы у границ ячеек
(`<ParaStyle:table_row>| <CharStyle:Bold>FRANCO-SCOTS<CharStyle:> | …` против
`<ParaStyle:table_row>|<CharStyle:Bold>FRANCO-SCOTS<CharStyle:>…`); содержимое, `<br>`,
жирные маркеры, порядок строк — идентичны. Структурно таблицы равны (критерий Task 4а —
«структурно равные исходным» — выполняется: сьют C8).

Сьют i2 правками не трогался (кроме фикса B3 из Task 0). Вариант решения (по вердикту):
сравнение для строк таблиц делать структурно (по числу таблиц/строк/ячеек и текстам ячеек), либо
питать CLI тем же нормализованным md — но это правка сьюта, требующая вашего решения.

## §9. Ограничения и что дальше

- Выравнивание «:---:» разделителя НЕ сохраняется (канон «|---|», решение TBL1.1 — в докстринге модуля).
- «<br>» и «**» в ячейках не обрабатываются — идут в текст как есть (решение зафиксировано в TBL1.0).
- Строки таблиц с разным числом ячеек сохраняются как есть (не выравниваются).
- Порядок строк таблицы при экспорте = порядок первого появления группы (после сортировки грида
  таблица всё равно собирается целиком, но порядок строк может отличаться от документа).
- Кандидаты вне этого батча: «Added to TM» безусловный лог (TBL1.0), колонка Type «TABLE_CELL»
  (косметика), .xlf-регенерация (конец серии), вердикт по i2 B9 (§5).
